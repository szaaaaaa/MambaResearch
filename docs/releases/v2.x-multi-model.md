# v2.x — Multi-model + Codex Workbench 集成（架构）

> **工作流文档见** [`v2.x-multi-subscription.md`](./v2.x-multi-subscription.md)——讲用户怎么同时使用 Claude Pro 订阅 + ChatGPT Pro 订阅两条管线；本文档讲架构层面"为什么这么设计 + 关键实现是什么"。

本文件对应 `docs/plans/2026-04-23-multi-model-subagent.md` 的 Task 6 输出，覆盖 Task 1 (provider registry) / Task 3 (subagent 分档) / Task 4 (role_models 废弃) / Task 5 (Codex Workbench 集成) 四组架构性变更。

## 1. Provider registry（Task 1）

**目标**：让 Workbench 后端支持"换 LLM 服务端点但不换 SDK"——核心 SDK (Claude Agent SDK) 保留，env 注入决定真实路由到哪个上游。

**实现**：`configs/agent.yaml` 的 `claude_code.providers` 段声明 provider 列表；`src/server/claude_code/providers.py` 解析为 `dict[str, ProviderConfig]`；session 创建路径按名查表，通过 `build_env_for_provider` 把 `base_url` + `api_key_env` 翻译成 SDK 子进程 env override（`ANTHROPIC_API_KEY` + `ANTHROPIC_BASE_URL`）。

**默认条目**（anthropic）：
```yaml
claude_code:
  providers:
    anthropic:
      base_url: https://api.anthropic.com
      api_key_env: ANTHROPIC_API_KEY
      default_model: ''
```

**扩展新 provider 的样板**：在 registry 加一个条目 + 确保对应 env 已设置，无需改代码。

**安全**：`/api/claude-code/providers` 端点不回传 `api_key_env` 字段（只是 env 名，但仍会泄漏服务端 env 布局，屏蔽）。

## 2. Subagent 分档（Task 3）

**目标**：让 Workbench 里的主 agent 有能力把子任务委派给更专业的子 agent，同时把"重成本模型（Opus）"限制在真正需要深推理的环节。

**单一事实源**：`.claude/agents/*.md`（YAML frontmatter + markdown body）。5 个标准角色：

| 角色 | 模型 | 职责 |
|------|------|------|
| `paper-searcher` | haiku | 多源论文检索 + 去重 |
| `evidence-extractor` | haiku | 从论文里忠实摘录原文证据段 |
| `analyzer` | sonnet | 证据→结论的合成推理，必要时跑代码验证 |
| `writer` | sonnet | 写稿 + 引用 |
| `critic` | opus | 严格质量评审（最后一关才调） |

**DP1 落地路径**：`ClaudeAgentOptions.setting_sources=["user"]` 让 CLI 只加载 user 层设置、跳过 project `.claude/settings.json`（为了让 `can_use_tool` HITL 桥生效）。副作用是 CLI 也不自动发现项目 `.claude/agents/`——fallback 是程序化注入：`src/server/claude_code/session_manager.py:_build_client` 读 `load_subagents_from_directory(...)` 的结果塞进 `options.agents`。

**测试**：`tests/test_claude_code_agents.py` 覆盖 5 文件结构 + 模型映射 + `_build_client` 注入机制。

## 3. `llm.role_models` 废弃（Task 4）

**原决策**：v1.0 时按"角色"分配模型（Retriever / Analyzer / Writer 分别 pin 到不同模型），`configs/agent.yaml` 的 `llm.role_models` 段做路由。

**新决策**：v2.0 废弃该段。理由：

1. **Skill 是黑盒单位，不该被 caller 看到内部模型决策**——skill 内部的 LLM 选择本应由 skill 自己实现。
2. **真正的分档在 subagent 层**（task 3）——`.claude/agents/*.md` 里的 `model:` 字段已经承担了"轻/中/重"的语义。
3. **Session 级 provider 选择已经存在**（task 1）——用户可在 Workbench 新建会话时选 provider。

**迁移路径**：`configs/agent.yaml` 的 `llm.role_models` 字段被删除；代码里对 `role_models` 的所有读取点被拿掉；`llm.provider` + `llm.model` 作为 skill runtime 的默认 LLM 入口。

## 4. Codex Workbench 集成（Task 5）

### 4.1 架构取舍

**前情**：项目原本只支持 Claude Pro 订阅（经 Claude Agent SDK → `claude` CLI → Anthropic）。用户需求变成"同时用 ChatGPT Pro 订阅"。历史上讨论过 4 条路：

| 方案 | 路径 | 结果 |
|------|------|------|
| A | 基于泄漏源码 fork claude-code-cli，加 Codex OAuth | 存档（`docs/plans/2026-04-24-claude-code-multi-auth.md`）；技术风险 + 法律灰区 |
| C | claude-code-router（CCR）反代到 DeepSeek / OpenRouter | 工作流 OK 但损失 Claude 订阅，没达到"订阅叠加"的目标 |
| D | OpenClaw / 第三方魔改 | Harness 不同，丢失 Claude 优化 |
| **F** | **双官方 CLI 并存 + `continues` bridge + Workbench 后端双 session manager** | **采纳** |

**为什么是 F**：

- 官方 harness 保留——Claude 家的 harness 和 Codex 家的 harness 各自针对自家模型调优，fork/代理都会引入翻译损失
- 订阅各自独立——Anthropic 从 2026-01 起封禁第三方用订阅 OAuth；CCR 只能 API key。F 方案让两个订阅各走各家 CLI
- Workbench 层统一 UI——同一个"新建会话"入口，provider 下拉选 claude / codex；后端按 provider 分派到对应 session manager

### 4.2 技术实现

#### Session manager 对偶（Task 5ba）

`src/server/codex/session_manager.py` 与 `src/server/claude_code/session_manager.py` 对偶：

```
CodexSessionManager
├── create / delete / get_or_restore / touch / interrupt / shutdown
├── idle TTL sweeper（60min 默认）
├── PermissionState（allowed_always 缓存 + pending_requests Future 表 + SSE emitter）
├── _build_permission_bridge（HITL approve / deny → JSON-RPC 响应）
└── _default_build_client（工厂——注入客户端，可被测试替换）
```

与 Claude 侧唯一差异：没接持久化 store（冷 session 暂不可恢复；错过 idle TTL 就 404）。加 `CodexCodeStore` 是后续任务。

#### JSON-RPC over stdio 客户端（Task 5bb）

`src/server/codex/app_server_client.py:CodexAppServerClient` 包装官方 `codex app-server --listen stdio://` 子进程：

- **Framing**: NDJSON（newline-delimited JSON），与 `src/mcp_bridge/server.py` 一致
- **Schema 守护**: `check_schema_compatibility` 首次 connect 跑 `codex app-server generate-json-schema`，缺关键 schema 抛 `CodexSchemaError`（DP7）
- **Reader demux**: 三类消息路由——`id+result/error` 解决 pending Future；`id+method` 服务端请求→bridge；`method` only→notification 推 turn queue
- **send_message**: async generator，`turn/start` → stream notifications → 命中终止 method（`turn/completed` / `connection/lost` / ...）则结束
- **OAuth 透明**: 不中转 token；codex 二进制自己读 `~/.codex/auth.json`

#### API 路由（Task 5c）

`src/server/routes/codex.py` 暴露 7 个端点形状对齐 `claude_code.py`：

```
POST   /api/codex/sessions               — create
GET    /api/codex/sessions               — list
GET    /api/codex/sessions/{id}          — single
DELETE /api/codex/sessions/{id}          — delete
POST   /api/codex/sessions/{id}/messages — SSE stream
POST   /api/codex/sessions/{id}/permissions — HITL decision
POST   /api/codex/sessions/{id}/interrupt   — cancel turn
```

前端在 `WorkbenchTab.tsx` 用 `sessionEndpointPrefix(session.provider)` helper 按 session 类型分派到 `/api/claude-code/*` 或 `/api/codex/*`；`SessionListItem` pill 按 provider 着色区分。

#### `/api/claude-code/providers` 的 codex 虚拟条目

Codex 不走 provider registry（用 ChatGPT OAuth，不经 Claude env 注入），所以**不**出现在 `configs/agent.yaml:claude_code.providers` 段里。但前端只有一个"新建会话" Modal，需要从**同一个端点**发现所有可用 provider。解决办法：`list_providers` 端点直接合成一个 `{name: "codex", base_url: "internal://codex-app-server", default_model: "gpt-5.5"}` 条目追加到返回列表。前端看到 `codex` 选项 → 创建时 dispatch 到 `/api/codex/*`。

#### Subagent 单一源 + 转换器（Task 5a）

由于 `.claude/agents/*.md` 是 Claude 原生格式，Codex 也需要自己的副本。`scripts/sync_subagents.py` 把 .md → `.codex/agents/*.toml`，pre-commit hook 确保两边不漂移。5 个文件生成 + 实测见下面"兼容性发现"章节。

#### v1.0 role vs v2.0 subagent 对比

形似神异——字面上都是"多个分工角色"，但运行语义截然不同：

| 维度 | v1.0 role | v2.0 subagent |
|------|-----------|---------------|
| 路由决策 | 硬编码规则（Planner rule-based） | LLM 意图驱动（主 agent 自己决定要不要委派） |
| Context | 共享同一个 Planner-维护上下文 | 独立线程；子 agent 拿"干净"上下文 |
| 载体 | 项目自写的执行框架 | Claude Agent SDK 原生机制 |
| 存在周期 | 永久身份（Planner 流程的一节） | Stateless，主 agent 需要时才 spawn |

## 5. Codex 兼容性发现（Task 5d）

本章节记录 Codex 侧对接实测遇到的问题，按"可接受"vs "需修复"分类。编写时间 2026-04-25。

### 5.1 已验证工作的路径（✅ 可接受）

**Session 生命周期**：create / list / get / delete 四路端点实测 200，真实 `codex app-server` 子进程正常 spawn + 正常退出，session 列表与内存状态一致。

**简单 turn 流**：prompt "reply with just the word OK" → 19 个 `codex_message` SSE 帧 + `codex_finished` 终止帧，send_message async generator 正常收尾，session 可以连续使用。

**MCP 桥挂载**：`.codex/config.toml`（项目级）写 `[mcp_servers.research_agent] command="python" args=["-m", "src.mcp_bridge.server"]`，codex app-server 启动时自动挑起 → SSE 可见 `mcpServer/startupStatus/updated {"name": "research_agent", "status": "ready"}`。与 Claude 侧同一份 `src/mcp_bridge/server.py` 对称工作。

**HITL 权限请求帧生成**：codex 在 read-only sandbox 下主动发起审批请求（如要访问 Write 类工具），我们的 reader demux 正确识别 `id+method` 形态、dispatch 到 `_build_permission_bridge`。简单 prompt 下 `codex_permission_request` SSE 帧可达前端。

### 5.2 发现的需修复问题（⚠️ 需修复）

#### F1. Subagent TOML 格式与 Codex 预期不兼容（Task 5a 改点）

**现象**：codex app-server 启动时实测输出 4 条警告：

```
Ignoring malformed agent role definition: failed to deserialize agent role file
at D:\ResearchAgent\.codex\agents\critic.toml:
invalid type: sequence, expected a map
```

5a 的 `scripts/sync_subagents.py` 输出的 TOML 顶层是 flat 的 `name = "..."` / `tools = [...]`，但 codex 期望嵌套 map 结构。即**codex 自己会自动加载 `.codex/agents/*.toml`（好消息）但格式要求和我们假设的不一样（坏消息）**。

**根因**：5a 设计时 codex 官方文档对 `.codex/agents/` 目录格式没公开完整 schema，converter 的字段布局是基于 Claude 侧 frontmatter 的猜测 + codex schema 的 `ExternalAgentConfigImportParams` 类型名反推。实测证明假设错。

**建议修复路径**：

1. 对照 codex 二进制对 `agent role file` 的实际反序列化 schema（可从 `codex.exe` 源码或 `ExternalAgentConfigImportParams.json` 推）
2. 更新 `scripts/sync_subagents.py` 输出结构——大概率是顶层加 `[agent]` 或 `[[agents]]` section
3. 重新 sync，验证 warnings 消失

**紧迫度**：P1（阻塞 Task 5d AC 3——无法测试 paper-searcher subagent 委派）

#### F2. `thread/start` 响应 schema 与 5bb 初版实现不匹配（已修）

**现象**：5bb 初版假设响应是 `{"threadId": "..."}`（flat），实测 codex 返回嵌套 `{"thread": {"id": "019dc1c7...", "preview": "", "status": {"type": "idle"}, ...}}`。连接失败，抛 `CodexSchemaError: thread/start returned no parseable thread id`。

**修复**：`CodexAppServerClient.connect` 的 thread id 解析按优先级：`thread_result["thread"]["id"]`（优先）→ `thread_result["threadId"]`（fallback）→ `thread_result["thread_id"]`（fallback）。已在 5d 本次会话内 landed。

**紧迫度**：已修（🟢）

#### F3. `_write_raw` check-then-use 竞态（已修）

**现象**：`_handle_server_request` 作为 fire-and-forget task 处理服务端审批请求后调 `_safe_write_response` → `_write_raw`。若期间 disconnect 把 `self._proc` 置 None，`_write_raw` 的 early-return 检查在 `await self._write_lock` 之前跑过，锁外检查结果已失效；拿锁后访问 `self._proc.stdin` 抛 `AttributeError: 'NoneType' object has no attribute 'stdin'`。

**非致命但吵**：`_safe_write_response` 的 `try/except Exception` 会捕获并 logger.exception，功能上不坏但 log 里总有堆栈。

**修复**：None 检查移到锁内（和使用同一临界段），抛 `RuntimeError` 而不是 AttributeError，被外层 try/except 归并。已在 5d 本次会话内 landed。

**紧迫度**：已修（🟢）

#### F4. 复杂 prompt 下 turn 异常截断（⚠️ 根因未定）

**现象**：同一 session，简单 prompt（如 "reply OK"）→ 正常 completed；但要求调 MCP skill 的 prompt（如 "call clarify_intent with user_request=..."）会导致 turn 在几帧 notification 后直接触发我方 reader 的 EOF → 合成 `connection/lost` 终止帧。assistant 生成 0 字符文本。

**方法出现频率**（一次失败 turn 实测）：
```
4  mcpServer/startupStatus/updated
3  warning  (都是 F1 的 malformed agent role)
3  item/started
2  thread/status/changed
2  item/completed
2  account/rateLimits/updated
1  turn/started
1  thread/tokenUsage/updated
1  connection/lost  ← 我方合成，说明 stdout 被关闭
```

**可能根因**（未验证）：
1. F1 的 malformed agent role warnings 在启动期累积，codex 可能在尝试初始化某个 subagent 失败后主动关闭连接
2. 我方对某个 server-initiated request 没回应（F3 的 race 导致写失败），codex 等超时后关连接
3. sandbox_mode=read-only 下 MCP tool 调用被 permission 卡住，我方审批路径出问题

**紧迫度**：P2——简单对话可用但复杂工作流不可用；短期用户只能用 Claude 走复杂任务，Codex 仅适合短对话。需要 F1 修复后再重测，F3 已修后也要重测。

#### F5. 部分 JSON-RPC approval method 名仍基于猜测（5bb F4 留下）

5bb `/fix` 阶段已对 `_APPROVAL_METHODS` frozenset 按 `ServerRequest.json` 修正 5 个名字，但 approval response format（`{"decision": "approve"}` vs `{"decision": "deny"}`) 和每个 approval 的 params 字段含义仍未实测对比 schema。F1 + F4 修复后重测时一并验证。

**紧迫度**：P3（需 F1/F4 先修）

### 5.3 已知限制（🔶 文档化，暂不修复）

#### L1. Codex session 无持久化，重启丢失

`CodexSessionManager` 暂无 `CodexCodeStore` 对偶；idle TTL evict 或 server 重启后 session 不可恢复，前端的 localStorage id 指向失效，`loadSessionById` 只查 `/api/claude-code/sessions/{id}/messages`（404 时清 id）——对 Codex session 同样 404 行为。使用上的限制：用户刷新浏览器会丢 Codex 对话历史。

**缓解**：重启前显式在对话里总结再新建 session；或者等后续任务加 `CodexCodeStore`。

#### L2. Codex 侧 subagent 委派与 Claude 的 Task tool 语义不对等（plan DP8）

Codex 的"subagent"（agent role definition）语义是"可以 `/agent <name>` 手动切换"——主 agent 不能像 Claude Task tool 那样程序化 spawn 一个独立 context 的子 agent 跑子任务。Plan DP8 预见到这点，决策是：**Codex 侧只承担"用户手动切 agent 做检索"这类轻度用法；重委派（多步自动 pipeline）留给 Claude**。

**前端 UI 建议**（后续任务）：Codex session 的 `/agents` 列表只展示"可切换 persona"而不展示"可 spawn 子任务"。

#### L3. Codex 侧不支持 `switch_model` / `clear_context` / `add_dir` 等运行时 mutator

Codex 的 thread 模型不允许运行时换模型或清上下文；这些功能只能新建 thread 实现。5c 的 `routes/codex.py` 故意不预埋 patch/command 端点。前端的 `/clear` `/add-dir` 等 slash 命令对 Codex session 会 404——目前 UI 没做 provider-aware 禁用，需要后续 frontend 调整（task 6 之外）。
