# MambaResearch 代码实现规范

状态：强制执行
适用范围：本规范生效后的全部新增、重构、修复和插件迁移代码
配套规范：[测试规范](03-测试规范.md)

## 1. 目的

本规范用于保证 MambaResearch 在插件化重构期间始终只有一套真实运行路径，避免新旧实现并存、
兼容代码累积、资源 owner 不清和设计文档互相冲突。

重构采用“分批彻底替换”，不是“在旧系统外再包一层”。每个实现批次必须交付完整的新路径，
切换唯一入口，并删除同一能力的旧代码、旧测试和失效设计。

## 2. 核心不变量

### 2.1 一个行为只有一个实现

同一业务行为在任意已完成版本中只能存在一个生产实现。

禁止保留：

- 新旧两套路由、service、adapter 或组件；
- 通过 feature flag 在新旧实现间切换；
- 调用失败后回退到旧实现；
- 仅为兼容旧调用方存在的 wrapper、alias 或 re-export；
- 注释掉的旧代码、`legacy` 目录和“以后删除”的 deprecated 分支。

版本控制承担回溯职责，生产代码不承担旧实现归档职责。

### 2.2 一个能力只有一个 owner

每项 capability 必须有唯一 owner。owner 独占负责：

- capability 注册；
- 配置解析和校验；
- 所拥有资源的启动与释放；
- 对外 route、provider、descriptor 或 UI contribution；
- 该能力的业务规则和错误语义。

Kernel、应用入口和其他插件不得重复启动、关闭或注册该资源。

### 2.3 一个能力只有一个入口

插件化能力只能通过受信任 catalog 和 typed registry 进入系统。禁止同时保留直接 import、手工
枚举、旧 startup hook 或旁路 service locator。

应用入口只负责装配：加载配置、解析插件、创建 registry、启动 lifecycle 和挂载 contribution；
不得重新知道具体业务插件名称。

### 2.4 新实现和旧实现不得跨批次并存

“新功能完成后删除旧代码”必须发生在同一个实施 Batch 内：

~~~text
实现新能力
  -> 验证新路径
  -> 切换唯一入口
  -> 删除旧实现
  -> 删除旧测试和旧配置
  -> 扫描残留引用
  -> 运行完整有效验证
~~~

不得把“删除旧实现”推迟到后续清理任务。若当前 Batch 尚不能安全删除旧路径，则该 Batch 尚未
完成，不能把新路径标记为正式实现。

## 3. 实施前要求

每个 Batch 开始前必须明确以下内容：

1. 原子行为合同：输入、输出、错误、状态迁移和资源边界。
2. 唯一 owner：迁移完成后由哪个 plugin 或 core module 负责。
3. 唯一入口：通过哪个 registry、route 或 UI contribution 消费。
4. 旧实现清单：需要删除的文件、函数、route、hook、配置、测试和文档。
5. 数据处理：是否存在需要迁移的持久化数据。
6. 验证命令：原子测试、集成测试、类型检查、构建或 smoke check。

没有旧实现清单的重构计划不得进入编码阶段。

## 4. 插件实现规则

### 4.1 Kernel 保持薄且稳定

Kernel 只拥有插件装配语义和 capability registry，不拥有具体业务流程。

Kernel 可以负责：

- manifest 和配置合同；
- catalog 校验；
- 依赖排序；
- typed registry；
- lifecycle 启动、回滚和逆序释放；
- 只读 capability snapshot。

Kernel 不得负责：

- backend transcript、conversation 或 PTY 数据面；
- research workflow 调度；
- 具体 UI 视图状态；
- 任意对象 service locator；
- 包扫描、远程插件、热重载或兼容入口。

### 4.2 Plugin 拥有完整垂直能力

插件可以复用稳定的 domain module，但不能把旧实现复制一份后改名为 plugin。迁移时应改变
owner 和装配入口；确需移动代码时，移动后必须删除原位置实现。

一个插件的注册和生命周期必须满足：

- `register()` 只贡献 descriptor、provider 或 route 引用，不启动资源；
- `start()` 只启动本插件拥有的资源；
- disposer 只释放本插件拥有的资源；
- 配置在启动边界一次性解析和校验；
- 插件之间只依赖明确合同，不读取对方内部状态。

### 4.3 不为未来能力预建框架

当前只有一个真实消费者时，优先实现最小合同和一个默认实现。只有下一项真实能力出现时，才扩展
对应 typed registry 或 adapter；不得预建通用 MCP、Research、UI 或 service container。

## 5. Backend 实现规则

每个 backend plugin 必须独占拥有自己的：

- descriptor 和 capability 注册；
- binary/auth 检测；
- new/resume 启动参数；
- session manager 或进程级资源；
- provider-specific 错误映射。

业务 route 只能通过 Backend Registry 解析 backend，不得直接 import Codex、Claude 或未来
backend 的具体实现。

迁移某个 backend 后必须删除：

- 旧 provider registry 条目；
- 旧 backend 分支和硬编码 ID；
- 重复的 auth probe；
- 旧 session 启动入口；
- 应用级重复 shutdown hook；
- 针对旧路径的测试和配置。

## 6. Frontend 实现规则

前端采用“核心重建、稳定叶子复用”，不整体复制旧前端形成第二套应用。

必须保持：

- 同一时刻一个可见工作区只挂载一个 Workbench；
- backend 选择来自 capability/conversation 合同，不由组件硬编码覆盖；
- 页面卸载时停止该页面拥有的轮询、订阅和 PTY；
- UI shell 只消费 view contribution，不枚举具体插件视图；
- API client、稳定展示组件和 design tokens 可以复用。

迁移一个页面或状态域后必须删除：

- 旧导航和旧渲染分支；
- 重复的全局/local 状态；
- 隐藏保活组件；
- 旧 backend 条件分支；
- 失效的 effect、定时器和事件订阅；
- 描述旧状态模型的注释和类型。

禁止通过永久隐藏旧组件来保存状态。需要跨视图保存的状态应由明确 owner 持有；视图只管理自身
生命周期。

## 7. 数据迁移规则

保留用户数据不等于保留旧业务实现。

存在旧数据时，按以下顺序处理：

~~~text
定义新 schema 和不变量
  -> 编写确定性 migration
  -> 使用真实旧数据形状验证 migration
  -> 切换所有 reader/writer
  -> 删除旧 reader/writer 和兼容分支
  -> 验证迁移幂等与数据保持
~~~

迁移代码只能承担数据转换，不能继续提供旧业务语义。若 migration 必须长期保留用于旧数据库逐级
升级，应保持 append-only、幂等且不被正常请求路径调用。

## 8. 删除规则

替换完成时必须同步删除所有关联残留：

| 类别 | 必须删除的内容 |
| --- | --- |
| 生产代码 | 旧函数、类、组件、route、hook、adapter、export |
| 装配 | 直接 import、手工枚举、重复 registry 条目、重复 lifecycle |
| 配置 | 旧字段、旧环境变量、旧默认值、失效 feature flag |
| 测试 | 旧实现测试、skip 测试、兼容测试、重复 fixture |
| 文档 | `docs/live` 中失效的结构、流程、接口和实施说明 |
| 注释 | 描述旧路径、旧阶段或已删除行为的注释 |

历史实现由 Git 保存。`docs/archive` 可以保存历史背景，但不得被当前实现、当前索引或
`docs/live` 作为有效设计引用。

## 9. 禁止的实现方式

以下实现不得合入：

- `old/new`、`legacy/v2` 两套实现并存；
- `try/catch` 后调用旧实现；
- null/default guard 掩盖错误状态；
- 为避免修改正确 owner 而在调用方逐个打补丁；
- 为单一实现创建没有真实变化点的 interface/factory；
- 一个全局 store 同时持有无关插件的业务状态；
- plugin 直接修改其他 plugin 的内部对象；
- 为未来功能创建空目录、stub、TODO 或占位 route；
- 用兼容 re-export 隐藏文件已经迁移的事实；
- 只删除入口但保留不可达旧代码。

## 10. 测试同步规则

实现和测试属于同一个 Batch，具体位置和数量遵守[测试规范](03-测试规范.md)。

重构时：

1. 先用新合同表述需要保留的行为。
2. 为新 owner 编写或迁移最小测试。
3. 新路径通过后删除旧实现测试。
4. 不复制旧测试文件形成 legacy/new 两套测试。
5. 集成测试只穿过新的唯一装配路径。
6. 完成 test-prune 后运行完整有效测试集合。

旧测试不因为覆盖历史行为而自动保留；只有仍属于当前合同的行为才重新表述。

## 11. 残留扫描

每个替换 Batch 完成前必须执行残留扫描。扫描目标至少包括：

- 被删除类型、函数和文件名；
- 旧 route path；
- 旧 plugin/backend ID；
- 旧配置字段和环境变量；
- `legacy`、`deprecated`、`fallback`、`compat`、`v1`、`v2`；
- 旧 startup/shutdown hook；
- skip、xfail 和被注释测试。

示例：

~~~powershell
rg -n "<old_symbol>|<old_route>|<old_config>" src frontend tests docs/live
rg -n "legacy|deprecated|fallback|compat" src frontend tests docs/live
git diff --check
~~~

搜索命中必须逐项判断并处理。不能以“当前不可达”为理由保留旧实现。

## 12. Batch 完成定义

一个实现 Batch 只有同时满足以下条件才能标记完成：

- 新行为合同全部实现，没有 stub、TODO 或空分支；
- capability 有唯一 owner 和唯一入口；
- 新路径已成为生产装配路径；
- 同一能力的旧实现和旧入口已经删除；
- 旧配置、测试、注释和 live 设计已经同步删除；
- 数据迁移已验证，正常请求路径不再读取旧格式；
- 原子测试和业务编排测试位于规定位置；
- test-prune 已完成；
- 残留扫描无未解释命中；
- 类型检查、构建、相关测试和 smoke check 全部通过；
- diff 不包含无关清理或未来占位实现。

任何一项不满足，该 Batch 都必须标记为未完成或部分完成，不能用“后续清理”关闭。

## 13. Code Review 门禁

Review 必须优先检查：

1. 是否出现第二套实现或第二个 owner。
2. 是否存在绕过 registry 的直接 import。
3. lifecycle 是否重复拥有同一资源。
4. 新入口切换后旧入口是否仍可达。
5. 旧测试、旧配置和旧文档是否仍然描述生产行为。
6. 数据迁移是否保持数据且终止旧运行时语义。
7. 新增抽象是否存在真实第二消费者。
8. 每一处新增代码是否属于当前 Batch 的行为合同。

发现上述问题时不得以兼容性或后续任务为理由通过 Review。
