# MambaResearch 测试规范

状态：强制执行
适用范围：本规范生效后的全部新增、重构和修复代码
上层计划：[实施文档索引](../技术实施文档/00-实施文档索引.md)

## 1. 目的

测试用于保护稳定合同和真实业务流程，不用于证明某个函数、类或文件已经被创建。

本规范解决四个问题：

1. 单元测试必须靠近所负责的原子功能。
2. 集成测试必须位于参与模块的最低公共父节点。
3. 一个功能使用尽可能少的测试文件。
4. 旧实现被替换时删除旧测试，不保留跳过、兼容或 legacy 测试墓地。

## 2. 核心原则

### 2.1 测行为，不测实现形状

优先测试：

- public contract 的输入、输出和错误语义；
- 生命周期、资源释放和状态迁移；
- 数据库 schema、migration 和数据保持；
- 安全、secret、路径和进程边界；
- 一个高价值业务流程的完整 happy path；
- 已经发生过且可能回归的真实 bug。

不单独测试：

- dataclass 字段能否赋值；
- getter 是否返回成员变量；
- mock 是否按预设返回；
- 私有函数被调用了几次，除非调用次数本身是资源/事务合同；
- framework 或标准库已经保证的行为；
- 同一分支的多个等价输入。

### 2.2 原子功能不等于一个函数

“原子功能”是一个可独立说明、实现和验证的最小行为合同。例如：

- Profile 能被解析并拒绝未知字段；
- 依赖图能稳定排序并报告闭环；
- Registry 拒绝重复 backend ID；
- lifecycle 在启动失败时逆序回滚；
- Codex adapter 能生成 new/resume 两种 argv；
- migration 保持旧数据并接受新的非空 backend ID。

一个原子功能可以由多个函数共同完成；不要按函数数量创建测试文件。

### 2.3 最小充分覆盖

每个非平凡原子功能默认只保留：

1. 一个主要成功路径；
2. 一个最重要的失败或边界路径；
3. 只有当另一分支会产生不同业务结果时，才增加用例。

同一逻辑的输入变体使用参数化测试，不复制测试函数。

## 3. 目录规则

Python 测试统一放在仓库根目录 <code>tests/</code>，不放入
<code>src/</code>，避免测试进入生产包或污染业务 package。

测试树镜像功能树：

~~~text
src/server/kernel/...
src/server/plugins/backend_codex/...

tests/
└── server/
    ├── kernel/
    │   └── test_kernel.py
    ├── plugins/
    │   └── backend_codex/
    │       └── test_backend.py
    └── integration/
        ├── test_codex_flow.py
        └── test_backend_migration.py
~~~

### 3.1 单元测试位置

单元测试放在对应叶子功能的镜像目录：

| 生产功能 | 单元测试 |
| --- | --- |
| <code>src/server/kernel/</code> | <code>tests/server/kernel/test_kernel.py</code> |
| <code>src/server/plugins/backend_codex/</code> | <code>tests/server/plugins/backend_codex/test_backend.py</code> |
| 未来 <code>src/server/plugins/backend_claude/</code> | <code>tests/server/plugins/backend_claude/test_backend.py</code> |

同一叶子功能的 loader、registry、lifecycle 可以在一个测试文件中用测试类或分段组织，不为每个
源文件建立一对一测试文件。

### 3.2 集成测试位置

集成测试放在所有参与功能的最低公共父节点。

示例：

- Kernel + Codex plugin + HTTP route 的流程属于 server 级，放
  <code>tests/server/integration/test_codex_flow.py</code>。
- Backend Registry + project database migration 也属于 server 级，放
  <code>tests/server/integration/test_backend_migration.py</code>。
- 只涉及同一个 research plugin 内部的 storage + service 时，放在该 plugin 镜像目录下的
  <code>integration/</code>。

不要把所有集成测试集中到一个全局大文件，也不要仅因为用了数据库就无条件上移到仓库顶层。

### 3.3 系统与 E2E 测试位置

只有跨越 server、frontend 和真实外部进程的自动化流程才进入：

~~~text
tests/system/
~~~

真实 Codex CLI 依赖本机安装和登录状态，不进入默认单元/集成测试。第一阶段只作为发布前 smoke
check；当它能在隔离 CI 环境稳定执行时，再创建系统测试文件。

## 4. 测试层定义

### 4.1 单元测试

单元测试满足：

- 不创建完整 FastAPI app；
- 不连接真实外部服务；
- 不启动真实 Codex/Claude CLI；
- filesystem 使用 <code>tmp_path</code>；
- 时间、binary lookup、环境变量和进程边界通过直接注入或 monkeypatch 控制；
- 一次只验证一个原子行为合同。

允许使用真实标准库对象，例如临时文件、纯内存 registry 和小型 sqlite connection；但跨越
schema migration、route 或多个 owner 时应归为集成测试。

### 4.2 集成测试

集成测试使用真实的内部装配：

- 真实 <code>create_app()</code>；
- 真实 Kernel loader/registry/lifecycle；
- 真实 FastAPI route；
- 真实临时 SQLite；
- 真实序列化和 API schema。

外部不稳定边界使用 fake：

- Codex binary 与真实认证；
- PTY/ConPTY；
- 网络服务；
- 用户主目录和真实项目数据。

Fake 必须实现 public contract，不能复刻被测模块内部逻辑。

### 4.3 Smoke test

Smoke test 只回答“真实环境的主路径能否启动”，不承担全面回归：

~~~text
MambaResearch start
  -> capabilities contains codex
  -> create conversation
  -> start Codex terminal
  -> receive first usable output
  -> close without orphan process
~~~

Smoke 失败需要阻止发布，但不应因本机未登录而让默认开发测试失败。

## 5. Codex-first 首批测试文件

首批只创建四个 Python 测试文件：

~~~text
tests/server/kernel/test_kernel.py
tests/server/plugins/backend_codex/test_backend.py
tests/server/integration/test_codex_flow.py
tests/server/integration/test_backend_migration.py
~~~

### 5.1 test_kernel.py

用分段或测试类覆盖：

- profile schema 与未知 plugin；
- dependency order、missing dependency、cycle；
- registry duplicate/unknown；
- lifecycle 正常逆序关闭、部分启动失败回滚、disposer 失败后继续清理。

相同错误类型的多组输入使用参数化，不拆 loader/registry/lifecycle 三个文件。

### 5.2 test_backend.py

覆盖：

- Codex new/resume argv；
- binary 查找顺序与缺失错误；
- provider 不支持错误；
- Codex auth 四种状态的参数化分类。

不启动真实 Codex 进程。

### 5.3 test_codex_flow.py

使用真实 app/Kernel/route 与 fake backend/PTY，覆盖：

1. profile 启用 Codex后，capabilities 与 auth 都只发布 Codex；
2. conversation 创建、terminal resolve、resume 和 served_by 形成一条完整编排链；
3. 未启用的 Claude/未知 backend 返回确定协议错误。

不要为 capability、auth、conversation、terminal 各建一个集成测试文件。

### 5.4 test_backend_migration.py

使用真实临时 SQLite，覆盖：

1. v6 数据升级后行数、字段值与索引保持；
2. 任意非空 backend/source 可写，空白值被拒绝；
3. migration 再次执行保持幂等。

一份完整迁移测试优先于为四张表复制四套相同流程。

## 6. Fixture 规则

Fixture 使用最窄作用域：

1. 只被一个测试文件使用：定义在该文件。
2. 被同一功能目录至少两个测试文件使用：放该目录 <code>conftest.py</code>。
3. 被多个 server 子域共同使用：才上移到 <code>tests/server/conftest.py</code>。
4. 禁止预先创建仓库根 <code>tests/conftest.py</code> 作为万能 fixture 集合。

Fixture 只负责建立状态，不隐藏业务操作和断言。测试主体必须能直接看出执行了什么业务行为。

## 7. Mock 与 Fake 规则

- 优先在进程、网络、时钟、filesystem root 和 CLI 等边界替换。
- 不 mock 被测函数的内部 helper。
- 不断言大段 mock call sequence，除非顺序是 lifecycle 合同。
- 一个公共 fake 被第二个测试文件需要前，先留在原测试文件中。
- 达到两个真实消费者后，才提取到父目录 fixture；不预建 fake framework。

## 8. 命名规则

测试名称表达“条件 + 结果”：

~~~python
def test_cycle_reports_dependency_path() -> None:
    ...


def test_start_failure_disposes_started_plugins_in_reverse_order() -> None:
    ...
~~~

禁止只描述函数名：

~~~python
def test_load() -> None:
    ...
~~~

测试文件按 capability 命名，不使用 batch、task 编号或日期。

## 9. 前端测试

前端当前没有独立测试框架。规则是：

- 类型、接口映射和纯 wiring 使用 <code>npx tsc --noEmit</code> 与
  <code>npm run build</code>；
- 出现包含分支的纯业务选择函数时，使用现有 <code>tsx</code> +
  Node <code>node:test</code>；
- 前端测试放在 <code>frontend/tests/</code> 下镜像功能目录；
- 不为简单 React 渲染、类型定义或静态 descriptor 引入 Vitest/Jest。

示例：

~~~text
frontend/src/api/terminal.ts
frontend/tests/api/terminal.test.ts

frontend/src/components/workbench/...
frontend/tests/integration/workbench.test.ts
~~~

只有出现真实非平凡前端行为时才创建对应测试文件。

## 10. 实施流程

每个代码 Batch 按同一顺序执行：

~~~text
1. 冻结原子行为合同
2. 实现一个原子功能
3. 在对应叶子目录补最小单元测试
4. 运行该测试文件
5. 完成一条跨模块流程
6. 在最低公共父节点补或扩展一个集成测试
7. 运行受影响测试
8. test-prune：KEEP / MERGE / DELETE / QUESTION
9. 运行完整有效测试集合
~~~

实现和测试属于同一 Batch，不允许先堆完所有生产代码再集中补测试。

## 11. Test Prune 门禁

每批完成后审查本批新增/修改测试：

| 分类 | 处理 |
| --- | --- |
| KEEP | 保护真实 contract、边界或高价值流程 |
| MERGE | 有价值断言并入更强的现有测试 |
| DELETE | 重复、实现细节、helper/mock/default 测试 |
| QUESTION | 业务价值不明确，确认后处理 |

禁止保留：

- 被 skip 的旧实现测试；
- 仅为覆盖率数字存在的测试；
- 对同一 branch 的重复 happy path；
- 大型 snapshot 且没有聚焦 invariant；
- <code>status_code in {400, 404, 500}</code> 这类不确定断言；
- 真实网络或真实用户凭据依赖的默认测试。

## 12. 执行命令

原子功能开发：

~~~powershell
pytest -q tests/server/kernel/test_kernel.py -p no:cacheprovider
pytest -q tests/server/plugins/backend_codex/test_backend.py -p no:cacheprovider
~~~

server 集成：

~~~powershell
pytest -q tests/server/integration -p no:cacheprovider
~~~

完整有效 Python 测试：

~~~powershell
pytest -q tests -p no:cacheprovider
~~~

前端：

~~~powershell
npm run lint
npm run build
~~~

CI 必须执行完整有效测试集合，不能长期维护一份手写测试文件白名单。

## 13. 验收标准

一个 Batch 的测试工作完成，必须同时满足：

- 每个非平凡原子功能有最小单元测试；
- 每条新增业务编排至少有一个集成 happy path；
- 关键失败边界有确定断言；
- 测试路径符合功能镜像树和最低公共父节点规则；
- 没有按源函数一对一拆分的冗余测试文件；
- 没有真实外部服务、用户凭据或用户目录依赖；
- test-prune 已执行；
- 目标测试、完整有效测试和前端构建均通过。

## 14. 旧测试清理决定

2026-08-15 起，重构前 <code>tests/</code> 基线全部删除，不保留 legacy 或 skip 版本。

后续不得从旧测试批量复制用例。需要保留的业务合同应根据新架构重新表述，并放入本规范定义的
功能镜像位置。
