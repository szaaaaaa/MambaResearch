## 3. 已冻结决策

1. Mamba Kernel 是薄宿主和装配器，不是 Agent Runtime。
2. Codex CLI 的本地 transcript 继续是真相源；SQLite 只保存编排元数据和镜像。
3. 第一阶段插件均为仓库内受信任 Python 模块，由显式 catalog 提供，不做目录扫描和动态下载。
4. Registry 只提供有类型的能力集合，不提供任意字符串到任意对象的 service locator。
5. <code>create_app()</code> 只完成配置读取、依赖校验、纯注册和路由挂载；进程资源只在
   FastAPI lifespan 内启动。
6. 启动失败立即失败，并逆序释放已经启动的资源；不保留旧路径、fallback、feature flag 或双路由。
7. 前端通过 <code>GET /api/capabilities</code> 获取 backend inventory，不再维护
   <code>'claude' | 'codex'</code> 联合类型。
8. 数据库中的 backend/source 字段保存稳定字符串 ID，不再使用固定枚举
   <code>CHECK</code>。
9. 当前只实现并启用 <code>backend.codex</code>；先打通 Codex Research MCP，不实现 Claude。
10. Backend seam 切换后不保留 Claude 旧终端路径；历史 Claude 元数据可读，但不能新建或
    resume，直到 Claude 插件完成。
11. 旧测试基线清零；后续测试统一按功能镜像树组织，并遵守
    [测试规范](../代码规范/03-测试规范.md)。

## 4. 明确不做

- 不引入 Cordis 依赖。
- 不实现远程插件、插件市场、包签名、权限沙箱或热重载。
- 不实现运行时远程 UI 代码。
- 不引入通用 event bus、通用 DI 容器或通用 hook 系统。
- Batch 1-3 不重写 PTY bridge、CLI transcript、MCP 协议或现有业务模块；协议升级只按独立专题
  规划执行。
- 不同时迁移 Research/UI 插件；Batch 3 只迁移 Research 后端能力，Batch 4 再迁移 UI seam。

这些能力只有在出现对应的真实使用场景后，才单独立项。

## 5. 实施批次

### Batch 1：Kernel 宿主

实施 [01-Mamba-Kernel-技术设计](01-Mamba-Kernel-技术设计.md)：

1. 新增最小 Kernel 合同、typed registry、profile loader 和 lifecycle。
2. 建立仓库内 built-in plugin catalog。
3. 将应用装配改为 <code>create_app()</code> + lifespan。
4. 用现有路由的薄插件完成注册，不移动业务代码。
5. 验证重复 ID、缺失依赖、依赖环和失败回滚。

Batch 1 结束时，应用行为不新增功能；Kernel 只是替代散落在
<code>app.py</code> 中的装配职责。

### Batch 2：Backend seam

实施 [02-Backend-Registry-技术设计](02-Backend-Registry-技术设计.md)：

1. 定义 <code>TerminalBackend</code>，先封装 Codex 启动逻辑。
2. 终端路由按 registry 查找 backend，删除所有名称分支和未插件化的 Claude 路径。
3. 新增 capability inventory，认证探测改为 backend 驱动。
4. 前端从 inventory 选择 backend。
5. 追加 SQLite migration，解除固定 backend/source 枚举。

Batch 2 结束时，增加一个测试 backend 只需要实现并注册 provider，不修改终端路由、
认证聚合器和前端 backend 类型；未来 backend 插件也使用同一接入方式。

### Batch 3：Research MCP seam

实施 [03-Research-MCP-Registry-技术设计](03-Research-MCP-Registry-技术设计.md)：

1. 增加 typed MCP Registry，一次迁移六个内建 Research MCP provider。
2. Workspace/Zotero plugin 同时接管自己的 HTTP route。
3. Codex new/resume 从同一 registry snapshot 生成 CLI config override，secret 只走 env。
4. 让 project <code>enabled_mcp_servers</code> 成为 profile 已启用集合的会话级子集。
5. 删除静态 <code>.codex/config.toml</code> 镜像、helper 自发现、旧 feature flags 和失效文档。

Batch 3 结束时，profile/plugin、MCP 管理 API 和 Codex 真实启动共享一个 Mamba-managed server
来源；禁用 Zotero 会同时移除其 MCP provider 和 API route。前端入口一致性由 Batch 4 完成。

### MCP 2026-07-28：协议升级专题

实施 [MCP 2026-07-28 协议升级规划](MCP-2026-07-28-协议升级规划.md)。该专题不占用已预留的
Batch 4 UI seam 编号，也不在 Codex 客户端兼容性未知时修改生产路径。先验证官方 SDK、Codex
new/resume 和 `paper_search_mcp`，再一次性替换手写协议并删除旧握手；Tasks、MRTR 和缓存分别
通过客户端门禁后独立实施。

## 8. 完成定义

Codex backend 纵向切片已经完成，完成定义为：

- 两个 Batch 的验收矩阵全部通过；
- 每个非平凡原子功能有最小单元测试，跨模块业务编排有集成测试；
- 旧装配与旧 backend 分支被删除，而不是保留为兼容路径；
- 当前 Codex PTY、resume、会话镜像和认证状态行为保持；
- 新 backend 的接入改动局限于一个插件模块和 profile/catalog 注册；
- 没有新增本阶段范围外的插件基础设施。

当前先完成 Batch 3 的真实 Codex smoke；Batch 4 仍是 UI seam。MCP 2026-07-28 专题只有在
Codex 客户端门禁通过后才进入实施，不得为协议兼容预建双路径。Claude 只有在 Codex Research
主路径稳定且出现明确需求后才单独设计；不得为 Claude 重开 Kernel、terminal、auth、frontend
或 schema 基础合同。
