## 1. 目标

在 Codex CLI 确认支持 MCP 2026-07-28 后，把 MambaResearch 的 MCP 实现从手写旧协议切换到
官方 Tier 1 Python SDK，删除旧握手、重复 JSON-RPC 循环和已弃用 transport，并按真实客户端
能力逐步采用 Tasks、Multi Round-Trip Requests（MRTR）和列表缓存提示。

升级必须保持现有控制面不变：

~~~text
Research plugin
  -> Kernel McpRegistry
  -> project enabled_mcp_servers
  -> CodexTerminalBackend launch injection
  -> Codex CLI MCP client
  -> MCP 2026-07-28 server
~~~

`McpRegistry`、Research plugin owner、project selection 和 secret env 注入已经解决能力装配问题；
本专题只替换 MCP wire protocol 和可由新协议直接承载的交互语义，不重新设计 Kernel。

## 2. 协议变化

| 旧协议 | MCP 2026-07-28 |
| --- | --- |
| `initialize/initialized` 握手和隐式 session | 请求自描述；无强制握手和 `Mcp-Session-Id`；可选 `server/discover` |
| server-to-client 请求依赖持续双向连接 | MRTR 返回 `input_required`，client 补充 `inputResponses` 后重试原请求 |
| HTTP gateway 解析 JSON body 后才能路由 | Streamable HTTP 使用 `Mcp-Method`、`Mcp-Name` header |
| list/read 响应需要重复拉取 | `ttlMs`、`cacheScope` 和确定性顺序允许客户端缓存 |
| Tasks 位于实验 core | Tasks 成为 `io.modelcontextprotocol/tasks` 正式扩展 |
| 扩展能力各自约定 | Tasks、MCP Apps、Enterprise Managed Authorization 使用正式扩展框架 |
| OAuth 依赖 Dynamic Client Registration | DCR 弃用，转向 Client ID Metadata Documents，并强化 issuer 校验 |
| HTTP+SSE、Roots、Sampling、Logging 仍可新增 | 进入至少十二个月的弃用窗口，新实现不得采用 |

新协议把 transport session 中隐藏的状态移出协议层。确需跨调用状态时，tool 必须返回显式 handle，
后续调用把 handle 作为参数传回；不得在 MambaResearch 内重新建立隐式 MCP session store。

## 3. 当前实现基线

### 3.1 已符合的部分

- 六个 Mamba-managed server 由唯一 Research plugin owner 注册。
- Codex new/resume 都从同一 `McpRegistry` snapshot 生成启动配置。
- managed provider 当前只有 `stdio`，没有远程部署和 OAuth 负担。
- Workspace、Zotero 和 History 每次 tool call 都按显式 project env 解析项目，不依赖 MCP session。
- provider 顺序稳定，适合向确定性 list 结果和客户端缓存演进。

### 3.2 需要替换的部分

- `src/server/mcp/probe.py` 手写 `initialize -> tools/list`。
- `src/server/mcp/sandbox.py` 手写 `initialize -> tools/call`。
- Workspace、Zotero、Experiment、Colab、Mamba History 各自复制 JSON-RPC stdin/stdout 循环，
  并处理 `initialize`、`initialized`、`tools/list` 和 `tools/call`。
- `pyproject.toml` 没有直接声明 MCP SDK；当前环境中的 `mcp 1.27.0` 不能作为项目依赖合同。
- MCP 控制台配置仍接受 `sse`，但 legacy HTTP+SSE 已被新规范弃用。
- Experiment 通过 `run/status/logs/cancel/metrics` 自行表达长任务生命周期。
- sandbox 的危险调用确认只保护控制台直调，不能覆盖 Codex 直接调用 MCP 的路径。

`paper_search_mcp` 是仓库外 server。协议核心切换前必须确认其发布兼容 MCP 2026-07-28 的版本；
不得在本仓库复制一份 paper search server 作为临时替代。

## 4. 冻结决策

1. Codex CLI 是当前唯一生产 MCP client；没有 Codex 兼容证据，不切换生产 server。
2. 使用支持 MCP 2026-07-28 的官方 Tier 1 Python SDK 作为唯一协议实现，不继续维护手写协议。
3. 一次切换所有仓库内 Mamba-managed server、probe 和 sandbox，旧协议代码同批删除。
4. `McpRegistry` 继续只保存 provider 合同，不解析 JSON-RPC、不缓存 tools、不承担 task 状态。
5. managed provider 在本专题内继续只支持 `stdio`；不为尚不存在的远程部署扩展 Kernel 合同。
6. 新能力只有在 Codex CLI 能消费并向用户呈现时才启用，不增加“仅 sandbox 可用”的第二套语义。
7. 不通过 feature flag、旧协议 fallback 或双 server entrypoint 维持两套生产路径。

## 5. 非目标

- 不实现 Claude MCP adapter。
- 不把 MambaResearch 改造成通用 MCP gateway 或托管平台。
- 不实现远程多租户、负载均衡、WAF、EMA 或 OAuth authorization server。
- 不为 Codex CLI 不支持的 MCP Apps 预建 renderer。
- 不把 pipeline/sub-agent 调度迁入 MCP Tasks；Tasks 只描述已有 Experiment 长任务。
- 不改变现有 tool 的研究领域规则、文件边界和 secret 来源。
- 不保留 `protocol_v1/protocol_v2`、`legacy` module 或运行时协议选择开关。

## 7. MCP-A：协议核心替换

### 7.1 原子行为合同

- Codex 可通过 stdio 对六个启用 server 完成 discover/list/call。
- 每个请求使用 MCP 2026-07-28 语义；server 不要求 `initialize/initialized`。
- tool 名称、input schema、返回 content 和业务错误保持现有合同。
- MCP 子进程仍由 Codex 或 sandbox 按需启动，调用结束后释放。
- protocol/SDK 错误明确失败，不回退到手写 JSON-RPC。

### 7.2 唯一 owner 与入口

| 能力 | Owner | 唯一入口 |
| --- | --- | --- |
| server protocol loop | 所属 Research plugin 复用的 server module | 官方 Python SDK server API |
| probe | `core.http` 的 MCP 管理能力 | 官方 Python SDK client API |
| sandbox call | `core.http` 的 MCP sandbox 能力 | 官方 Python SDK client API |
| provider selection | Research plugin / Kernel Registry | 现有 `McpRegistry` snapshot |
| Codex transport | `backend.codex` | 现有 CLI `-c mcp_servers...` 注入 |

### 7.3 同批删除

- 五个仓库内 server 的 `_handle_initialize()`。
- 五个 server 对 `initialized` / `notifications/initialized` 的分支。
- 五个 server 重复的 stdin/stdout JSON-RPC dispatch loop 和 frame helper。
- `probe.py`、`sandbox.py` 中手写的 protocol version、initialize payload、response matcher。
- 只验证旧握手或私有 frame helper 的测试和注释。
- 任何临时 SDK wrapper、协议版本开关和旧协议 fallback。

domain tool 函数、schema 构造、ExperimentRunner、Workspace/Zotero/History service 不复制、不迁移
到第二个 package；SDK handler 直接调用现有 domain 函数。

### 7.4 依赖处理

- 在 `pyproject.toml` 直接声明并固定支持 MCP 2026-07-28 的稳定 Python SDK 版本。
- 不依赖 `claude-agent-sdk` 或其他包的传递依赖提供 MCP SDK。
- 同批升级并验证 `paper_search_mcp`；如果没有兼容版本，MCP-A 不得标记完成。

## 8. MCP-B：Transport 合同清理

1. Mamba-managed provider 继续只暴露 `stdio`，不修改 `McpStdioConfig`。
2. 从 writable `.mcp.json` API、类型、校验、前端选项和 live 文档删除 legacy `sse`。
3. 当前没有真实 HTTP probe/call consumer，因此不新增 Streamable HTTP 占位实现。
4. Codex 原生配置中的外部 HTTP server 仍由 Codex 自己读取；Mamba 管理 API 不宣称拥有其
   启动、认证或健康检查。
5. 出现真实远程 MCP 需求时另立 Streamable HTTP 技术设计，并一次实现 header 路由、OAuth、
   probe/call 和资源释放，不恢复 HTTP+SSE。

若数据清点发现 `.mcp.json` 含 `sse`：不自动把 URL 改写为 Streamable HTTP，因为 endpoint
语义不能由字符串安全推断；PATCH/启动边界返回包含 server ID 和配置路径的明确错误，要求用户
提供新的 endpoint。不得静默删除或把失败 server 当作禁用。

## 9. MCP-C：Tasks、MRTR 与缓存

本批只有在对应 C4 门禁通过后实施；每项都替换现有行为，不并行保留两套入口。

### 9.1 Experiment Tasks

- `research.experiment` 继续拥有 ExperimentRunner 和业务 policy。
- 长任务状态通过 `io.modelcontextprotocol/tasks` 暴露，使用 `tasks/get`、`tasks/update` 和需要时的
  `subscriptions/listen`。
- 迁移 pipeline skill 和 UI 消费者后，删除被 Tasks 覆盖的重复 status/cancel 协议与测试。
- `logs`、`metrics` 只有在 Tasks 未表达对应领域数据时才保留为 domain tool。
- 数据库 `experiment_runs` 仍是业务记录；MCP task handle 是协议标识，不成为第二份运行真相源。

### 9.2 MRTR 审批

- 删除以全局 tool 名单判断危险性的第二套策略；风险规则由拥有 tool 的 Research plugin 定义。
- 需要确认或补参数时，server 返回 `input_required`；client 提供 `inputResponses` 后重试原调用。
- 拒绝确认时不得执行文件写入、实验启动、取消或外部 API 修改。
- Codex 与 Mamba sandbox 必须消费同一 server-side 规则；不能只在前端隐藏按钮。

### 9.3 列表与资源缓存

- `tools/list`、`resources/list`、`resources/read` 的顺序保持确定性。
- 只对确实稳定的目录返回 `ttlMs` 和 `cacheScope`；project、凭据或 profile 变化后必须使结果失效。
- 不在 Kernel 新增第二个工具目录缓存；缓存提示属于 MCP server response，是否缓存由 client 决定。

## 10. 明确延期的扩展

| 能力 | 当前决定 | 重新评估条件 |
| --- | --- | --- |
| Streamable HTTP | 不实施 | 出现需要独立部署或共享访问的真实 server |
| Header-based routing | 不实施 | MambaResearch 自己托管远程 MCP gateway |
| CIMD / issuer-bound OAuth | 不实施 | 接入需要 OAuth 的远程 Mamba-managed server |
| Enterprise Managed Authorization | 不实施 | 出现组织级集中身份和策略需求 |
| MCP Apps | 不实施 | Codex 或 Mamba Workbench 有真实 app renderer 和用户流程 |
| `server/discover` UI | 不实施 | UI 确实需要启动前展示动态 capability，而非静态 Registry |

延期项不创建 contract 字段、空目录、stub route、feature flag 或配置占位符。

## 11. 数据与配置

- Kernel profile、`enabled_mcp_servers`、env override 和 SQLite schema 不因 MCP-A 改变。
- server/tool 稳定 ID 保持不变，现有 project selection 直接生效。
- MCP-A 不自动重写用户 Codex 配置；Codex 原生 config 继续由 Codex 管理。
- MCP-B 对 legacy `sse` 先清点、再明确失败，不进行不可验证的 URL 自动转换。
- MCP-C 如改变 Experiment task ID，必须定义确定性映射并验证已有 `experiment_runs` 可读；不得
  修改历史 migration 或复制运行记录。

## 12. 最小测试矩阵

### 12.1 MCP-A

- 一个代表性 server 使用官方 SDK client 完成 discover/list/call，覆盖无握手请求。
- 参数化验证六个 plugin 的 tool catalog 可由同一 SDK 路径读取，不复制六份测试文件。
- 一个业务失败用例验证 MCP error 不被改写为成功 content。
- probe 与 sandbox 各保留一个真实子进程流程，验证关闭后无遗留进程。
- 已登录 Codex new/resume 分别调用 Workspace tool，并确认 cwd 等于会话项目。

### 12.2 MCP-B

- writable config 拒绝 `sse` 且错误包含 server ID，不修改原文件。
- 当前 stdio custom server 仍可 list/probe/call。

### 12.3 MCP-C

- Experiment task happy path 和 cancel path 各一个，验证 runner 与 task 状态一致。
- MRTR 接受与拒绝各一个，拒绝路径验证副作用没有发生。
- 一个稳定 tool list 验证顺序和 cache hint；不测试 SDK 自身缓存实现。

## 13. 验证命令

每个实施批次必须执行其最小测试，然后执行：

~~~powershell
pytest tests
npm.cmd run lint --prefix frontend
npm.cmd run build --prefix frontend
git diff --check
~~~

MCP-A 真实 smoke：

1. 使用已登录 Codex 从 active research project 启动 new 会话。
2. 确认所选六个/子集 server 可见并调用 Workspace tool。
3. resume 同一会话并再次调用 tool。
4. 关闭会话，确认无遗留 Codex PTY 或 MCP 子进程。
5. 对一个 MCP 2026-07-28 fixture 记录实际请求，确认没有旧 initialize/session 依赖。

残留扫描至少执行：

~~~powershell
rg -n "_handle_initialize|notifications/initialized|Mcp-Session-Id" src tests docs/live
rg -n "transport.*sse|Literal.*sse|stdio / http / sse" src frontend tests docs/live
rg -n "legacy|deprecated|fallback|compat|xfail|skip" src frontend tests docs/live
git diff --check
~~~

搜索命中必须逐项解释；协议发布说明中的历史描述可以保留，生产代码、测试和 live 当前行为说明中
不得残留旧入口。

## 14. 实施顺序

1. 完成 C1-C5 兼容与数据门禁，不修改生产路径。
2. 实施 MCP-A，一次切换官方 SDK server/client 并删除手写协议。
3. 实施 MCP-B，删除 legacy SSE 和无效配置说明。
4. 分别验证 Tasks、MRTR、cache 的 Codex C4 门禁。
5. 只实施门禁已通过的 MCP-C 子能力，每项同批删除被替代语义。
6. 完成 test-prune、残留扫描、完整测试和真实 Codex smoke。

不得为了“先兼容”而交换步骤 2 的切换与删除顺序；MCP-A 未完成时不叠加 Tasks/MRTR。

## 15. 完成定义

### MCP-A 完成

- 所有仓库内 server、probe、sandbox 只使用官方 MCP 2026-07-28 SDK 路径。
- Codex new/resume 与 `paper_search_mcp` 真实 smoke 通过。
- 手写 initialize、dispatch loop、frame helper、旧测试和旧注释已删除。
- 没有协议 feature flag、fallback 或兼容 wrapper。

### MCP-B 完成

- writable Mamba config 不再接受 legacy `sse`。
- stdio 是唯一由 Mamba 管理并实际 probe/call 的 transport。
- live 文档与 UI 不再宣称存在未实现的远程能力。

### MCP-C 子能力完成

- 对应 Codex 客户端门禁已通过。
- 新扩展成为唯一生产入口，被替代的 tool/status/confirm/cache 语义已删除。
- 行为测试、完整测试、构建、残留扫描和真实 smoke 全部通过。

任一条件未满足时，对应批次保持“未实施”或“部分完成”，不能用 SDK 的向后兼容能力在项目代码
中保留旧实现。
